# Printed CLIs

## Purpose

`tools/` holds **printed CLIs**: standalone Go command-line tools generated by
[CLI Printing Press](https://github.com/mvanhorn/cli-printing-press) and vendored into this
repository as repo tooling.

They live here for one reason: the harness drives external services that have their own operational
surface, and an agent working in this repo should be able to reach for a real, tested tool for that
service instead of hand-rolling HTTP calls. ComfyUI is the first — the harness's media generation
(`offload_generate_image`, `offload_run_graph`) submits graphs to a local ComfyUI server, and
`comfyui-pp-cli` is the purpose-built way to inspect, submit, time, and attribute those renders from
the shell.

A printed CLI is **generated code that we adopt, not code we author here.** That distinction drives
every rule below.

## Questions this doc answers

- Why is there a second Go module inside this repository?
- What may I edit in `tools/`, and what must I never edit?
- How does a printed CLI get updated when the Printing Press improves it?
- What layout must the next printed CLI follow?
- What does CI run for these modules, and why is it a separate job?

## Scope

The `tools/<api>/` trees, their build and test contract, and the adoption/re-vendor cycle that keeps
them in step with the upstream Printing Press.

## Non-scope

- **The harness's own media pipeline.** How the harness decides what to render and on which GPU is
  [systems/media-generation.md](media-generation.md). A printed CLI is an operator/agent tool beside
  that pipeline, not a component of it — the harness does not shell out to `comfyui-pp-cli` at
  runtime.
- **Generation itself.** Research, codegen, verification, and scoring happen in the Printing Press
  runstate on the machine that prints, not in this repo.

## Key concepts

- **Printed CLI** — a complete, self-contained Go module produced by one Printing Press run. It
  carries its own `go.mod`, tests, README, agent skill, and release config.
- **Printing** / **reprint** — a full regeneration from the API spec under the current Printing
  Press. A reprint replaces the generated tree wholesale; it is not a patch.
- **Vendoring** — copying a promoted printed CLI out of the Printing Press library into
  `tools/<api>/` here. This repo is the tool's *distribution* home, not its *source of truth*.
- **Provenance record** — [`tools/comfyui/.printing-press.json`](../../tools/comfyui/.printing-press.json),
  which records the Printing Press version, run id, spec checksum, verify result, and scorecard for
  the exact tree that was vendored. Read it before assuming anything about how current a tool is.

## How the system works

### Separate Go modules, deliberately

Each printed CLI keeps its own `go.mod` with the module name the Printing Press gave it
(`comfyui-pp-cli`), **not** a package path under `github.com/dmmdea/offload-harness`. This is the
load-bearing structural choice:

- Go excludes nested modules from a parent's `./...`, so the harness's `go build ./...`,
  `go vet ./...`, and `go test ./...` do not see `tools/` at all. The harness's dependency graph
  stays exactly as small as it was.
- A printed CLI pulls dependencies the harness has no business acquiring — `cobra`, `mcp-go`,
  `modernc.org/sqlite`. Merging the modules would inject all of them into the harness binary.
- A reprint can replace the whole tree without touching the harness module.

The cost is that nothing in `tools/` is covered by the harness's default commands. That is why CI
runs a separate job per printed CLI (below); without it, these modules would rot silently.

### The regenerate / re-vendor cycle

```
spec  ──►  Printing Press run  ──►  library/<api>  ──►  promote  ──►  tools/<api>/  (this repo)
             (research, codegen,      verify, polish,                   vendored,
              verify, score)          dogfood, score                    reviewed, merged
```

Changes flow in **one direction**. When a printed CLI needs to improve:

1. Run the Printing Press workflow (`/printing-press-polish` for targeted fixes,
   `/printing-press-reprint` for a full regeneration) against the CLI in the Printing Press library.
2. Let it verify and score there.
3. Re-vendor the promoted tree into `tools/<api>/` and open a PR here.

Do **not** fix a generated file by editing it in this repo. A subsequent reprint overwrites the whole
tree and the fix disappears with no diff to explain it — the same failure mode as editing generated
tier pages instead of `setup/templates/profiles.json`. Fix it upstream so the next print carries it.

`.printing-press-patches/` is the generated tree's designated slot for deviations that genuinely must
live in the vendored copy. It currently holds only `.gitkeep` for `comfyui-pp-cli` — there are no
local patches, and adding one should be rare and explained in its PR.

### What is vendored and what is not

Vendored: all Go source, `go.mod`/`go.sum`, `spec.yaml`, the MCP generation inputs
(`manifest.json`, `mcp-descriptions.json`, `tools-manifest.json`), `.printing-press.json`,
`.printing-press-patches/`, `examples/`, and the documentation set (`README.md`, `SKILL.md`,
`AGENTS.md`, `CLAUDE.md`, `CHANGELOG.md`, `LICENSE`, `NOTICE`, `Makefile`, `.goreleaser.yaml`,
`.golangci.yml`).

Not vendored, and ignored in `.gitignore`:

- `build/` and `bin/` — compiled binaries and the `.mcpb` MCP bundle. The ComfyUI bundle alone is
  ~20 MB; binaries never enter this repo.
- Run reports (`dogfood-results.json`, `workflow-verify-report.json`,
  `apify-actor-audit-report.json`, `.printing-press-*-polish.json`) — evidence from one machine's
  run, superseded by the next one. The durable summary already lives in `.printing-press.json`.

Note that the root `.gitignore`'s `/bin/` rule is anchored to the repo root and does **not** cover
`tools/*/bin/`; the `tools/*/` rules exist precisely because of that.

## Layout contract

Every printed CLI adopted here follows the same shape, so the next one lands without re-litigating
any of this:

```
tools/<api>/                 # <api> is the API name, matching .printing-press.json "api_name"
  go.mod                     # module <api>-pp-cli — never folded into the harness module
  cmd/<api>-pp-cli/          # the CLI entry point
  cmd/<api>-pp-mcp/          # the MCP stdio server entry point (when the CLI is MCP-ready)
  internal/                  # generated implementation
  SKILL.md                   # the agent skill — the entry point agents should read
  AGENTS.md, CLAUDE.md       # per-tool agent guidance (CLAUDE.md is a one-line @AGENTS.md include)
  README.md, CHANGELOG.md    # human docs
  .printing-press.json       # provenance record
  .printing-press-patches/   # local deviations from the generated tree; normally empty
```

Adopting a new one means: vendor the tree, add a CI job mirroring the existing one, add a routing
line to the root [`AGENTS.md`](../../AGENTS.md), and list it in this doc and the root `README.md`.
`llamaswap-pp-cli` is the next expected arrival and lands at `tools/llamaswap/`.

## Dependencies

Each printed CLI depends only on its own `go.mod` graph and Go 1.26+. It does not import the harness,
and the harness does not import it. `comfyui-pp-cli` additionally expects a reachable ComfyUI server
at runtime — but not at build or test time.

## Downstream effects

Vendoring or re-vendoring a printed CLI does not change harness behavior: no harness package imports
`tools/`, and the harness's build and test commands do not reach into it. The blast radius of a
change here is the tool itself, its CI job, and this doc.

## Invariants and assumptions

1. **`tools/*/` modules are never merged into the harness module.** Nested `go.mod` is the isolation
   boundary.
2. **Generated files are not hand-edited here.** Fix upstream and re-vendor; use
   `.printing-press-patches/` only for deviations that cannot live upstream.
3. **No binaries, no run reports.** Enforced by `.gitignore`.
4. **Every printed CLI has a CI job.** A module invisible to the root `./...` and absent from CI is a
   module that is not actually tested.
5. **Tests stay offline.** A printed CLI's `go test ./...` must pass with no live server.

## Testing notes

From the module directory:

```bash
cd tools/comfyui
go build ./...
go vet ./...
go test ./... -count=1
```

`comfyui-pp-cli` has 17 packages with tests, all passing offline. The suite reaches the network only
to assert a *failure* path (`ProbeReachable` against a closed port), so an ubuntu CI runner with no
ComfyUI installed is a valid host for the full suite — no packages are excluded and no mock-mode env
var is needed. The Printing Press verify-mode variables (`PRINTING_PRESS_VERIFY`,
`PRINTING_PRESS_VERIFY_LIVE_HTTP`, `PRINTING_PRESS_DOGFOOD`) govern the Printing Press's own verify
and dogfood runners, not `go test`, and CI leaves them unset.

CI runs this as a dedicated `tools-comfyui` job in `.github/workflows/ci.yml`, parallel to the
harness `build` job.

## Common pitfalls

- **Running `go test ./...` from the repo root and believing it covered `tools/`.** It did not — Go
  skips nested modules. `cd` into the module.
- **Editing a generated file to fix a bug.** It works until the next reprint, then vanishes. See the
  cycle above.
- **Assuming the vendored tree is current.** Check `.printing-press.json` — its `run_id` and
  `printing_press_version` describe the run that produced *this* tree, not the latest Printing Press.
- **Confusing `comfyui-pp-mcp` with the harness MCP server.** Two different servers with different
  tool surfaces. The harness's is `local-offload`.
- **Adding the tool's dependencies to the harness `go.mod` to "share" them.** That reintroduces
  exactly the coupling the module split prevents.
