### Fixed - a render on a reused ComfyUI instance no longer reads as "still to load" for its whole run

- **What was wrong.** The host-RAM term of the grant subtracts what a lease's job already holds from what it declared, and it read only the processes below the lease's holder. A keyed ComfyUI instance is launched under one lease and kept: the next lease on the same cards reuses it, and its runner restamps the instance's launch marker with that lease's epoch, but the python process stays below the launcher that started it, which is not below the new holder. So a render on a reused instance counted its whole declared need as still to load for as long as it ran, and every other request on the box was judged against that memory twice. Seen on the 3-card reference box during a run of video clips: `gpu status` printed `29.9 GiB commit still to load` four minutes into a clip whose instance held 31.3 GiB private; a request for the third card would have needed the host to fit the clip's 30 GiB a second time.
- **What it does now.** The reading of a live lease adds the memory of every live keyed instance whose launch marker names the epoch of a live lease of the same holder and that is not already below the holder; an instance launched by the lease's own runner is counted once. The marker's recycled-pid rule applies. A marker that names no epoch ties nothing here. What a NEW request declares is unchanged.
- **Checks.** On that box, during a clip: the released binary printed `29.9 GiB commit still to load`, a build with the fix printed `0.9 GiB commit still to load` for the same lease (the instance held 29.1 GiB private at the time). The package's existing host-RAM, tree and marker tests pass.
