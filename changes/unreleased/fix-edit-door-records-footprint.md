### Fixed - the generative edit door records its render footprint (VRAM and host peaks) like the image door, and a card-only music render is recorded under its own key

- **What was wrong.** A real `edit-image-generative` render finished correctly but `footprints.json` gained no entry for it: the edit door passed no sampling hook (the image, video, animate, audio and run-graph doors do), so the store held nothing to read about what an edit render held on a host, and `calibratedRAM` had no history to raise an edit call's declared host need to.
- **What it does.** The edit door now records under `(edit family, quant, image-edit)`: the family is the one the edit need names (`qwen-image-edit-2511` when `gen_edit_family` is unset, else `qwen-image-2.1`), the quant is the bound qwen-image-2.1 precision and `multicard` (or `<precision>+multicard`) under `gen_edit_placement: multicard`, and the task is the fleet's own `image-edit`. The edit need carries the same key, so three measured runs raise a later edit call's declaration like an image call's. The music door records a card-only render (`musicgen_placement: multicard`) as `(acestep, multicard, audio-gen)` and a single-card one as `(acestep, "", audio-gen)` as before, and the music need carries the same key. The voice path's key is unchanged. Entries recorded before this release stay as they are: music runs from a card-only placement sit under the single-card key until the window turns over.
- **Checks.** One case added to `TestTheCardOnlyPlacementHasItsOwnFootprintKey`.
