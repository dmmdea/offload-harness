### Fixed - a fleet pipeline job gets the node's harness binary and ComfyUI input folder

- **What was wrong.** A node that serves a pipeline CLI as a fleet task type (`pipelines.<task_type>`, for example `scene-swap`) started the CLI with the node's environment and nothing else. The CLI then fell back to its own defaults for the two things it needs from the node: the harness binary (`local-offload` looked up on `PATH`) and the ComfyUI input folder (a Windows path). On a Linux node the binary sits in the service's own folder and ComfyUI lives elsewhere: read on the two-card Linux reference node, the service's `PATH` does not hold the binary and the Windows input path does not exist, so the node would advertise the task type in its health while a job's first nested call had nothing to start. It worked on a Windows node only because the CLI's defaults happened to match that machine.
- **What it does now.** The pipeline-job runner adds two names to the child's environment: `LOCAL_OFFLOAD_BIN`, the node's own executable, and `COMFY_INPUT`, `<comfy_dir>/input`, the folder every render script of the harness uses. A name the node's environment already sets is inherited unchanged, so an operator's value wins, and an unset `comfy_dir` sets no `COMFY_INPUT`. On a Windows node whose `comfy_dir` is the default, `COMFY_INPUT` equals the CLI's old default, so nothing moves there. `docs/FLEET-NODE.md` (Pipeline-job task families) states what the CLI gets, and that the config path still travels by `LOCAL_OFFLOAD_CONFIG` in the service unit.
- **Checks.** `go build ./...`, `go vet ./internal/pipeline/` and `go run ./cmd/changelog check`; one scene-swap job through the fleet door of a Linux node with two 16 GB cards.
