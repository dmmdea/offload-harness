### Fixed - an accelerator answers while the node's GPUs are leased, and a shared accelerator tool falls back to the next device

- **Why.** Two rules kept accelerators idle while callers waited, both seen 2026-11-11. A text lease on a node's GPUs made `/fleet/dispatch` refuse every forwarded accelerator call with `node leased` for the whole measurement window, although an `accel` job runs on an NPU or TPU and never on a leased card. And a shared tool (`offload_object_detect`, `offload_classify_image`, `offload_image_embed`, `offload_semantic_segment`) had one owner and no second choice (ADR 0068: "nothing falls back at call time"), so with the owner's node off or refusing the tool deferred while two other devices that serve the same name were reachable.
- **What it does: the lease.** A GPU lease never refuses an `accel` job (`fleetnode.textLeaseAgainst`). Every other task type keeps its reading, and the lease is published in health as before.
- **What it does: the fallback.** The owner of a shared tool is tried first. When it cannot take the call (a defer, or a sidecar refusal about the device such as a missing model or a disabled NPU), the call runs on the next device that serves the name, in the listed order, through that device's own tool row and with only the arguments its schema declares. The answer carries `fallback: {from, reason, served_by}`; when no device answers, the owner's defer carries `fallback_tried`. A refusal of the caller's input is the answer and is not retried elsewhere. Nothing is remembered between calls. Both surfaces (the MCP tools and the agent loop) use one function, `agent.AccelFallback`, and a node running a forwarded job still cannot forward again.
- **Embeddings.** `offload_image_embed` and `offload_text_embed` move to another device only when the caller passes `any_space: true`, because that vector is in another space; without it the defer carries `fallback_withheld`. The argument is added to the schema only on a box where a fallback device exists.
- **Safety.** One security pass ran on the change; both findings are fixed here. A fallback could hand `out_path` to a device whose sidecar checks nothing: the Coral's `semantic_segment` overwrote any path it was given, the caller's own image included. The fallback now applies the lane's rule before any device runs (`out_path` is never the input image, its directory must exist, an existing target is replaced only when it is a regular PNG file; otherwise the defer carries `fallback_withheld`), and the Coral sidecar applies the same rule itself and writes through a temporary file. A fallback device that answers JSON `null` is a defer, not a crash.
- **What a caller sees.** A tool with a fallback device carries a `FALLBACK:` sentence in its description (kept by the compact tools profile), and `offload_status.accelerators.<id>.fallback_for` lists the names a device answers for another owner. A box with one device, or with no shared name, advertises exactly what it did.
- **Check.** Two tests, one per incident: an `accel` dispatch under a text lease is admitted while an image job on the same node is still refused, and through the MCP surface a tool whose owner has no node to reach runs on the next device with the owner named, an embedding stays put without `any_space`, and `any_space` never reaches a sidecar.
- **Docs.** ADR 0102 (supersedes one consequence of ADR 0068), `docs/systems/accelerators.md`, `docs/systems/gpu-lease.md`, the operator guide's lease paragraph.
