### Fixed - a forwarded accelerator call writes its mask or depth map on the caller's box instead of returning the bytes

- **Why.** A fleet accelerator tool called from a box without the device (the Axera card's `offload_segment`, `offload_semantic_segment` and `offload_depth`, the Coral's `offload_semantic_segment`) answered with the node's PNG as 40-110 KB of base64 inside the tool's answer (`mask_b64`, `depth_b64`), wrote no file, and dropped the caller's `out_path`, although each tool says it writes a PNG and returns its path. Seen 2026-11-11 driving the Axera card from the delegator.
- **What it does.** Before the answer is returned, every file the node shipped back (`<stem>_b64` + `<stem>_name`) is written on the caller's box and `<stem>_path` names it: at the caller's `out_path` when there is one shipped file, otherwise beside the caller's image as `<image>.<kind>.png`, the local lane's default. The bytes leave the answer.
- **Safety.** The landing name is built on the caller's box: the node only contributes `<kind>`, a plain word, and a result key that is not a plain word is dropped, so a node's answer can never name the caller's image, a sibling file or another directory. `out_path` is never the input image (an agent-loop model could pass both the same) and its directory must exist, as for the sidecars. Only PNG bytes land; an existing file is replaced only when it is a regular PNG file, never a symlink or any other kind of file (the sidecars' own `out_path` rule), and a file that cannot land leaves `<stem>_error`. The MCP surface and the agent loop both forward through this path. One security pass ran on the change; its two findings (a node-chosen key climbing out of the image's directory, a node-chosen name replacing the caller's image) are fixed here.
