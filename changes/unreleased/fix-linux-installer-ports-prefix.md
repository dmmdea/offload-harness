### Fixed - the Linux installer follows --listen in the harness config, takes a start port, checks the port, and makes --prefix absolute

- **What was wrong.** `setup/install.sh --listen 127.0.0.1:11437` rendered llama-swap for 11437 but wrote no `endpoint` into the harness config, so the harness kept talking to the default 11436, which on a shared box can be another product's llama-swap. There was no start port for the models, a re-run without the flag went back to 11436, and nothing checked whether the port was already taken. Separately, `--prefix stack` was stored as given, so the config, the systemd unit and the client-mode MCP registration held a relative path that broke as soon as they started from another directory, while the acceptance gate, run from the same directory, still passed.
- **What it does now.** `--prefix` is made absolute right after the options are read. `--start-port N` (and `OFFLOAD_SWAP_START_PORT`, 1024..64000) is passed to the render, and `--listen` is checked to be `HOST:PORT` with a port in 1024..65535. A new `config.json` gets `endpoint` from the listen port, and an existing one has a loopback endpoint moved when `--listen` is given. With both flags unset, a re-run reads the listen address and start port back from the `# basis:` line of the existing `llama-swap.yaml`. Before anything is written, a live run connects to the listen port and stops when something answers that this install did not render for; `--dry-run` only says it would. The children's port range is not probed.
- **Checks.** `bash -n setup/install.sh`; `setup/install.tests.sh` passes (its live runs now name a free port); with a stub binary, a relative `--prefix` printed the absolute path, `--listen`/`--start-port` reached the render call and the new config, a re-run kept both, a kept config's endpoint moved, bad values were refused, and a held default port stopped a fresh install before any file was written.
