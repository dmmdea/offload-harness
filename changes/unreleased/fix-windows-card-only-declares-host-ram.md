### Fixed - a measured card-only recipe with no Windows figures no longer declares 0 host RAM on a Windows host

- **What was wrong.** A card-only (`--placement multicard`) row that was measured declared 0 host RAM on every host. The 0 is a Linux measurement: there the read-only map's pages are clean file pages `MemAvailable` already counts. On a Windows host the same render holds real memory, the map's pages in the working set and the card allocations in system commit: this box's own footprint records show a krea2 card-only render at 27 GiB resident and 31 GiB of commit, and a qwen-image one at 16.6 and 24.5 GiB, while the door declared 0 for both. Only `flux3-klein/bf16` carried Windows figures.
- **What it does.** On a Windows host a measured card-only row that fits the two leased cards but carries no `hostWindowsGiB` keeps the ordinary estimate, and the declaring line says why: its 0 was measured on a Linux host and no run has measured what a Windows host holds for it. Once a run on Windows has measured a row, its figures go in `render/multicard-recipes.json` (`hostWindowsGiB`) and the row declares them, stated, as `flux3-klein/bf16` does. Linux is unchanged (0, marked card-only).
- **Checks.** `TestAMeasuredCardOnlyRowDeclaresItsWindowsFiguresOnlyOnAWindowsHost` carries the new case. The tests that pin the Linux zero now say Linux (`imgFacts` sets `GOOS`; the pipeline tests that run the real door expect the zero only off Windows).
