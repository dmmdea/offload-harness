### Fixed - the Windows installer no longer dies on a failed HyperFrames refresh or a node that errors on --version

- **What was wrong.** On Windows, a box whose HyperFrames already met the floor but was older than npm's newest release tried to refresh it on every installer run. One transient registry, disk or antivirus error in that refresh threw out of the whole installer: the harness exe had already been rebuilt, but the install manifest was never written, the config step never ran, and the staging folder stayed behind. A node shim that wrote to stderr on `--version` (a version manager with no default Node set, a bad `NODE_OPTIONS`) did the same under Windows PowerShell 5.1. The same stderr trap hit `git ls-remote` in the Vulkan engine build script (the depth engine) and the `go build` in the renderer test script on a cold module cache, and the config reads in the installer decoded a UTF-8 config as the ANSI code page, so a non-ASCII `comfy_dir` was mangled.
- **What it does now.** A failed refresh of an install that meets the floor warns and keeps the installed version, which still goes through `npm audit signatures` (a failure there stays fatal); the staging folder is removed. Any other failure of the HyperFrames step warns, leaves the compose lane unbound and carries the previous manifest record, so the install finishes. A node that errors on `--version` takes the existing "no usable node" skip. The stderr cases are read on the exit code instead, and the installer's config reads use UTF-8. When `go build` of the harness exe fails, the error names any running processes that hold the exe open.
- **Checks.** Parse check of the three scripts with Windows PowerShell 5.1; the installer itself was not run. The Go and shell installers were not changed.
