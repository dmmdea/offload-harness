### Added - a lease waiting for host RAM can ask the WSL VM to drop its page cache (`gpu_hostram_wsl_cache_drop`, off by default)

- **Why.** On a Windows host the WSL 2 VM's page cache (files a distro has read) is committed memory to the host, and no Windows reclaim touches it. On the reference box WSL's own reclaim left about 25 GiB of it in place for over 40 minutes while a render's lease waited on host RAM with no seat loaded. One manual drop moved the host's commit from 127.0 to 103.2 GiB and the render started.
- **What it does.** With `"gpu_hostram_wsl_cache_drop": true`, a request refused on host RAM that will keep waiting (the grant's queue wait, and the wait after `--unload-seat`) asks once, in the background: it reads `/proc/meminfo` through a distro that is already running (it never starts one), and only when the cache a drop can free (`Cached` less `Shmem`) covers the request's shortfall does it run `sync` and `drop_caches=1` as root. Every process on the box together makes at most one attempt a minute (a stamp file beside the lease directory). Each drop writes one stderr line with the droppable cache before and after; a failure writes one line too. The next tick's reading of the host is what admits the request.
- **Where it does nothing.** Off Windows, with no running distro, under an account that sees none, when the droppable cache does not cover the shortfall, for a request with no `--wait`, and for the agent seat's cold-load gate (a single check, not a wait).
- **Docs.** `docs/systems/gpu-lease.md` ("The WSL VM's page cache"), the key's row in the operator guide, `config.example.json`.
