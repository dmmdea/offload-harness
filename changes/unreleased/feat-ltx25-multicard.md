### Added - the card-only two-card placement runs LTX-2.5: `--wan-placement multicard --model ltx25`, and the typed `video` door can choose it from config

- **What it does.** `--wan-placement multicard` (`render/wan-multicard.mjs`, `render/wf-ltx25-i2v.mjs`, `render/comfy-video.mjs`) also places the LTX-2.5 family (`--model ltx25`); every other non-Wan model and a `--graph` file are still refused. The 20.03 GiB int8 convrot DiT and the 14.32 GiB Gemma text encoder run pooled across the lease's two non-display cards through DisTorch2, the donor being the other card and never system RAM. The roles' device numbers are the reverse of the Wan placement's, because an int8 DiT that computes on any device other than cuda:0 faults with an illegal memory access (ComfyUI-MultiGPU issue #220, archived upstream, no fix coming): the launch (`multicardLaunch`, `order: "compute-first"`) lists the compute card first in `CUDA_VISIBLE_DEVICES`, so cuda:0 is the compute card and cuda:1 the storage card. That launch has its own instance key, `mcc-<compute uuid head>-<storage uuid head>`, so a kept storage-first ComfyUI (`mc-...`) is never reused for LTX-2.5 or the other way round, and the device check after the start (`checkComfyDevices`) compares cuda:0 with the compute card and cuda:1 with the storage card. The Wan and image launches are unchanged. The graph (`multicard: { residentGb, teAllocation }` on `buildLtx25I2V`; the single-card and `poolVvramGb` paths are untouched) loads the DiT through `UNETLoaderDisTorch2MultiGPU` (`compute_device` `cuda:0`, `expert_mode_allocations` `cuda:0,<R>gb;cuda:1,*`, `virtual_vram_gb` 0, `donor_device` `cpu`, `eject_models` false, `weight_dtype` `default`), the encoder through `OffloadCLIPLoaderDisTorch2` (`type` `ltxv`, `device` `cuda:0`, split `cuda:0,7gb;cuda:1,*`) and both VAEs through `VAELoaderMultiGPU` on `cuda:1`. The DiT and the encoder (34.4 GiB) do not fit the two cards (31.8 GiB) together, so a new node of the harness's pack, `OffloadFreeAfterEncode`, sits between the prompt's conditioning and the two guiders: it drops the encoder from ComfyUI's loaded-model list, empties every weight it holds on a card, returns the cached blocks to the driver, logs each card's memory before and after, and stops the run with `OFFLOAD-TE-STILL-RESIDENT` if any of the encoder's tensors is still on a CUDA device, all before the first sampler places the DiT (the pack runs with `--cache-none`, so the next prompt builds and places the encoder again). `--wan-resident-gb` is, for LTX-2.5, the GiB of the DiT kept on the compute card (default 9, so the storage card holds the other 11 GiB and both VAEs). The planner refuses before ComfyUI starts a share the compute card plainly cannot hold (more than its size less the 1 GiB latent upscaler and 0.5 GiB of context, 14.4 GiB on a 15.9 GiB card), a share that leaves the storage card more than it holds, a non-`.safetensors` or bf16 (about 39 GiB) `--transformer`, and `--pool-vvram-gb`; it keeps the display-card refusal, the lease cross-check and the pack check (the MultiGPU pack and the harness's own). Typed door: `videogen_placement: multicard` (flat key or `videogen_families["ltx25"].placement`, with `videogen_wan_resident_gb` for the share) leases the box's two non-display cards as a set, passes `--wan-placement multicard` (and `--wan-resident-gb` when configured), drops the single-card pin and dynamic VRAM and the pool flags, and declares the stage-rule host RAM through `hostneed.ForVideoCardOnly` (0 GiB when the DiT's share, the latent upscaler and the context fit the compute card and the rest of the DiT, both VAEs and the context fit the storage card; the encoder is gone before the DiT lands); a `.gguf` or bf16 transformer is refused before any lease. `doctor` lists the card-only graph's node classes for the pack check.
- **Why.** The house rule is that every model bigger than one 16 GB card runs pooled across the two non-display cards with DisTorch2, with the other GPU as donor and never system RAM. LTX-2.5 had only the older ratio-mode pooled path (`poolVvramGb`, a virtual-VRAM donor), which is not that placement, and the Wan one could not be reused as is: its storage-first card order puts the int8 DiT's compute on cuda:1, the case that faults upstream.
- **Check.** The one new test asserts the LTX-2.5 launch lists the compute card first under a key distinct from the storage-first one and that the LTX-2.5 graph's DiT computes on cuda:0; two existing tests that pinned LTX-2.5 as an unplaced family now use another family. The planner, the multicard graph and the launch were read back from real calls with a synthetic card table (the compute card first in `CUDA_VISIBLE_DEVICES`, `mcc-` key, the node inputs above, and each refusal), and `OffloadFreeAfterEncode` was exercised on a stand-in model on the CPU. **No GPU render was run for this change**: the resident share (9 GiB) and the encoder split (7 GiB) are chosen, not measured, the sampler's activations at LTX-2.5's geometry are unmeasured (the planner says so with an `LTX-PLACEMENT-NOTE` on every run and does not size them), and the encoder release has not been seen on a card. The operator runs it next.
