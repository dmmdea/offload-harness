### Fixed - the keep-comfy render test no longer leaves its folder behind when the stub's teardown is slow, and the render test folder removal rides out a busy folder

- **The defect.** The test "a runner given keep-comfy exits after its job while the instance it launched stays up" failed once in a full render suite run on a loaded Windows machine: its cleanup killed the detached stub with `taskkill` and removed the folder at once, `removeTree` gave up after about 2.75 s of linear retries (10 tries, 50 ms apart and growing), the removal threw `EPERM` and the `comfy-keep-*` folder survived. `taskkill` returns before Windows has finished tearing the tree down; a process that is still exiting keeps its working directory and its open files. Two such folders from earlier runs were found in the test temp dir, each with a console log that ended mid-line (a stub killed, a folder that stayed).
- **The fix (test support only).** `render/test-scratch.mjs` gains `killTree(pid)` (the tree is listed before the kill, with the same `descendantsOf` the runners use, or read from `taskkill /T` output on Windows) and `awaitTreeGone(pids, { timeoutMs })` (polls the killed pids for up to 10 s, prints one line if the bound passes, never throws). `removeTree` now retries `EPERM`, `EBUSY` and `ENOTEMPTY` from 50 ms doubling to 1 s per step for about 15 s, and still throws when the folder cannot go and at once on any other error. `scratchDir(t, prefix, { teardown })` runs a teardown ahead of the removal, which is how the keep-comfy test's folder now comes from `scratchDir` while the kill still happens before the removal; its entry left the raw `mkdtemp` allow-list. It was the only render test with the kill-then-remove shape.
- **Tests, red first.** `removeTree: a folder a child keeps busy for 4 s is removed once the child lets go` (a child holding the folder as its working directory plus an open file, Windows only) failed 3 of 3 on the old `removeTree` with `EPERM` and passes on the new one. The back-off sequence, the three transient codes, the bound, the immediate throw on another code, the `awaitTreeGone` wait and its bound line, and `killTree` of a parent with a child are pinned with a fake clock or a real process tree.
- **What was not shown.** Busy-loop CPU starvation (6 burners on two cores, below-normal priority, 20 runs; then one core; then normal and high priority burners, started up front and started after the runner exited) never reproduced the `EPERM`. The only failures it produced were the runner's own 15 s start budget, a different fragility. The old code and the fixed code both passed 20 of 20 in the first shape, and the fix with either half removed did too; the busy-folder test above is the proof of the back-off (the old `removeTree` is its red), and the wait is covered by its own tests, not by a load shape. Measured under the first shape, `awaitTreeGone` returned in 0 to 1 ms in all 20 runs: the killed pids were already gone when `taskkill` returned, so the wait is insurance against a lag that was not observed on this machine, and what held the folder in the one field failure is unconfirmed.
