### Fixed - the GPU lease admits host RAM on the memory that is available and on the commit limit, not on committed memory against physical RAM

- **The defect.** The host-RAM brake admitted a lease only while `committed memory now + the lease's declared need + what running leases have yet to load` stayed under physical RAM less the headroom. Committed memory is not memory in use. On the reference 3-card Windows box (127.7 GiB RAM, 171.7 GiB commit limit) a reading of 70.5 GiB committed with 75.6 GiB physically free refused a 72 GiB arm, and a coder-model arm whose process tree touched 27.8 GiB and was charged 58.1 GiB could not be admitted at all (70.5 + 58.1 = 128.6 against 119.7). A job that commits twice what it touches does charge twice, but the line that charge can run into is the OS commit limit, not physical RAM.
- **The rule.** A grant now needs two conditions, each against the line that is real for it (`gpuprobe.HostRAMAdmitsLoad`, the one function the grant, the read-only check, the card allocator's pre-filter and the deferred-lease wait all call): the working set the job touches must leave the headroom of the memory that is available (`available - touched need - what running leases have yet to touch >= headroom`), and its commit must fit the OS commit limit (`commit charge + commit need + what running leases have yet to be charged <= commit limit - headroom`). A quantity declared as 0 is not judged. A touched need above physical RAM less the headroom, or a commit above the limit less the headroom, is refused at once. A refusal names the condition that failed and its numbers (`needs 28.0 GiB, only 30.0 GiB of 127.7 GiB physical is available, 8.0 GiB headroom`, or `needs 58.1 GiB of commit, committed 150.0 of 171.7 GiB commit limit, 8.0 GiB headroom`), and both when both failed.
- **Interface.** `gpu reserve --ram <GiB>` keeps its meaning as the touched working set. The new `--ram-commit <GiB>` is the commit; unset it is the `--ram` figure (estimated or given), so every existing caller, the media admission and the seat warm-back included, keeps a commit condition at least as strict as its touched one, now against the commit limit. An explicit `--ram-commit 0` is refused rather than read as "same as `--ram`", and a commit needs a `--ram` above 0 to go with. A job whose commit is smaller than its working set (mapped files) cannot say so by leaving the flag out: it is judged on the larger figure, and `--ram-commit` states the smaller. The hold bound (`--ram-hold-max`, `gpu_hostram_hold_max_sec`) and the front-waiter behaviour are unchanged.
- **The record and the surfaces.** The lease record carries `host_ram_commit_gib` and, for `--unload-seat`, `host_ram_wait_commit_gib` (additive, omitted when equal to the touched figure; an older reader judges the lease by `host_ram_gib` alone). The detached holder takes `--ram-commit` and `--ram-wait-commit`. `gpu status` shows both declarations of a live lease (`host RAM 10.0 GiB touched, 60.0 GiB commit`), and the `host_memory` block of `gpu status --json` and of `offload_status` gains `declared_live_commit_gib`, `pending_commit_gib`, `commit_limit_enforced`, `touch_room_gib`, `commit_room_gib` and `verdict_why`; the lease rows gain `host_ram_commit_gib` and `host_ram_wait_commit_gib`. `internal/mcpserver/testdata/offload_status_default.golden.json` was regenerated on purpose for those additive keys (`OFFLOAD_UPDATE_GOLDEN=1`; no existing key changed).
- **The verdict word follows the rule.** `OK`, `NEAR` and `OVER` used to compare the commit charge to physical RAM, a line the grant no longer applies, so a status line would have said the box was over while leases were being admitted. They now judge the same two lines: `NEAR` is the available memory or the room under an enforced commit limit inside the headroom (a new lease that declares host RAM waits), `OVER` is one of them gone (nothing available, or the charge at an enforced limit). The reading of 2026-10-09 (3.2 GiB available, 162.9 GiB committed of a 187.7 GiB limit) reads `NEAR`, not `OVER`. It still does not claim the box is paging.
- **Linux.** The commit condition is applied only where the kernel enforces a limit: `vm.overcommit_memory` = 2. In the default heuristic mode (0) and in mode 1 the kernel grants allocations past `CommitLimit` and `Committed_AS` counts mappings a process reserved and never touched, so the reading is marked soft (`HostMemory.CommitLimitSoft`) and only the available condition applies. A mode that cannot be read is not assumed strict, and neither is a `/proc/meminfo` that hides the commit counters. Two Linux nodes of the fleet were both in mode 0 on 2026-10-17, so on them the commit condition is moot.
- **Not-yet-loaded accounting, per quantity.** What running leases have yet to touch is their declared working set less what their processes hold resident; what they have yet to be charged is their declared commit less what their processes hold privately (private bytes are the currency of the commit charge). Each is pooled per holder and never below zero, and a holder that cannot be read holds nothing. The holder-memory test seam now reports both.
- **How it was proved.** Red first at each layer, with the failure lines in the commit messages: `internal/gpuprobe` (the table of conditions, the Linux reader through its file seam in strict, heuristic, always, unreadable and hidden-accounting cases, the Windows counters conversion), `internal/gpulease` (both directions through the grant, the pending accounting, the deferred wait, the record), and the root package (the flags, the holder arguments, the unload-seat wait with a commit the unload does not free enough, `gpu status`). The three required mutants went red (each condition removed; the commit compared to physical RAM again), and so did the mutants listed in the pull request. The documented readings are pinned by tests, among them the coder arm of 27.8 GiB touched and 58.1 GiB charged against the 70.5 of 171.7 committed and 75.6 available (`TestMeasuredCoderArmIsAdmittedAgainstTheCommitLimit`) and the two-lane incident of 2026-10-09 with a realistic available figure (`TestTheTwoLaneIncidentIsStillRefused`). The tests' fake hosts moved to a commit limit equal to physical RAM, which keeps the arithmetic of every existing commit scenario; their refusal strings name the commit limit.
- **Not verified here.**
  - No lease was taken and no seat was loaded: every test runs against a stand-in host reading, so nothing here shows the admission on a live box under a real lease.
  - The coder-arm and llama.cpp figures (27.8 and 3.6 GiB touched, 58.1 and 32.1 GiB charged) and the 70.5 of 171.7 GiB reading are session measurements, not re-run for this change.
  - The Linux strict-mode branch has no live host: both Linux nodes read are in mode 0, so the strict path is exercised through the reader seam only.
  - The Windows commit limit under page-file growth at run time, and the 1:1 charge of VRAM allocations to commit on nodes other than the reference box, are not measured.
  - The default for `--ram-commit` is the touched figure; taking the commit from the private peak the footprint store already records for a lane's process tree is a follow-up.
